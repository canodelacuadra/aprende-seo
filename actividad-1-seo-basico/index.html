Antes de empezar

Esta actividad no es un tutorial para copiar y pegar. Cada paso explica qué haces, por qué importa para el SEO y cómo comprobar que está bien. Al final entregarás una web real publicada y un conjunto de evidencias.

Objetivos de aprendizaje

  • Crear una web estática de tres páginas con HTML5 semántico y CSS.
  • Configurar los elementos de SEO on page: title, meta description, encabezados y alt.
  • Entender y aplicar URLs amigables, canonical, noindex y redirecciones 301.
  • Crear robots.txt, sitemap.xml y una página 404 correcta.
  • Publicar con GitHub Pages y verificar el sitio en Google Search Console.
  • Medir el resultado con Lighthouse o PageSpeed Insights.

Qué necesitas

  • Visual Studio Code con la extensión Live Server.
  • Una cuenta de GitHub (gratuita) para publicar con GitHub Pages.
  • Una cuenta de Google para usar Search Console.
  • Un navegador con DevTools: Chrome, Edge o Firefox.
  • Una imagen con licencia libre relacionada con la informática. Puedes usar Unsplash, Pexels o Pixabay.

La empresa ficticia

Durante las tres actividades trabajarás con la misma marca: TecnoSerprofes, un servicio técnico de reparación y mantenimiento informático situado en Toledo. Mantener la misma marca y ubicación te permite comparar resultados entre actividades y evitar contenido duplicado.

Errores frecuentes al empezar

  • Usar mayúsculas, espacios o tildes en nombres de archivo y carpetas. Rompe enlaces en servidores Linux.
  • Guardar las imágenes en el escritorio y no dentro de img/.
  • Copiar el mismo title en las tres páginas.
  • Confundir la dirección local (file:///) con la dirección publicada.

01 Crear la estructura del proyecto

Un proyecto ordenado evita enlaces roscos y facilita el despliegue.

Objetivo del paso

Tener creada la carpeta del proyecto con las tres páginas, la hoja de estilos y la carpeta de imágenes.

Abre Visual Studio Code, crea una carpeta llamada tecno-serprofes y dentro esta estructura:

tecno-serprofes/
├── index.html
├── servicios.html
├── contacto.html
├── 404.html
├── robots.txt
├── sitemap.xml
├── css/
│   └── estilos.css
└── img/
    └── reparacion-ordenador.webp

Los archivos 404.html, robots.txt y sitemap.xml los crearás más adelante. Ahora basta con las tres páginas, css/ e img/.

Comprueba

En el explorador de VS Code deben verse exactamente esos nombres, en minúsculas. Si tu sistema oculta las extensiones, actívalas en el explorador de Windows para no crear index.html.txt.

02 Construir la página principal con HTML semántico

La estructura del documento es la base sobre la que se apoya todo el SEO on page.

Objetivo del paso

Crear index.html con etiquetas semánticas, un title único, una meta description propia y una jerarquía de encabezados correcta.

¿Estática o dinámica?

Una página estática se sirve tal como está guardada: el HTML, el CSS y el JavaScript no se generan en cada petición. Una página dinámica se construye en el servidor (por ejemplo, con PHP y una base de datos) cada vez que alguien la visita.

Para el SEO, la ventaja de lo estático es que el contenido ya está en el HTML inicial: el rastreador no depende de ejecutar JavaScript y la página suele cargar más rápido. Aun así, sigue siendo necesario trabajar las palabras clave, los metadatos, los enlaces y la publicación.

Escribe el documento

<!DOCTYPE html>
<html lang="es">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Reparación de ordenadores en Toledo | TecnoSerprofes</title>
  <meta name="description" content="Servicio técnico y reparación de ordenadores en Toledo. Mantenimiento informático y asistencia para particulares y empresas.">
  <link rel="stylesheet" href="css/estilos.css">
</head>
<body>
  <header>
    <a href="index.html">TecnoSerprofes</a>
    <nav aria-label="Navegación principal">
      <a href="index.html">Inicio</a>
      <a href="servicios.html">Servicios</a>
      <a href="contacto.html">Contacto</a>
    </nav>
  </header>

  <main>
    <section>
      <h1>Reparación de ordenadores en Toledo</h1>
      <p>
        En TecnoSerprofes ofrecemos servicios de reparación y mantenimiento
        informático para particulares y empresas.
      </p>
      <p>
        Nuestro objetivo es ayudarte a mantener tus equipos informáticos
        en perfecto estado.
      </p>
    </section>

    <section>
      <h2>¿Qué servicios ofrecemos?</h2>
      <p>
        Realizamos reparaciones de ordenadores, mantenimiento de equipos
        y asistencia técnica.
      </p>
      <a href="servicios.html">Consulta nuestros servicios de reparación</a>
    </section>
  </main>

  <footer>
    <p>© 2026 TecnoSerprofes · Toledo</p>
  </footer>
</body>
</html>

Qué hace cada elemento

Elementos SEO del documento HTML
ElementoFunción SEODónde va
lang="es"Indica el idioma del contenido a navegadores y buscadores.Etiqueta <html>
<title>Título de la pestaña y, normalmente, enlace en la SERP. Debe ser único, descriptivo y contener la keyword principal.<head>
meta descriptionResumen de la página. No es un factor de ranking directo, pero influye en el CTR y Google puede reescribirla.<head>

Cuidado con los encabezados

No uses los encabezados para cambiar el tamaño del texto: para eso está CSS. Tampoco pongas varios h1 ni saltes de h2 a h4. La jerarquía debe reflejar la estructura real del contenido.

Comprueba

  • Abre la página con Live Server, no con doble clic sobre el archivo.
  • En DevTools → Elements, confirma que el title y la meta description están dentro de <head>.
  • La pestaña del navegador muestra el título completo.
  • Solo hay un h1 y los h2 cuelgan de él.

03 Crear la página de servicios

Cada página debe tener su propio título, su propia descripción y su propia intención.

Objetivo del paso

Crear servicios.html con metadatos propios, tres apartados h2 y enlaces internos descriptivos.

Copia la estructura de index.html, cambia el contenido y sustituye el title y la meta description. No reutilices los de la portada: si dos páginas comparten título, compiten entre sí y empeoran la relevancia de ambas. 

<title>Reparación y mantenimiento informático en Toledo | TecnoSerprofes</title>
<meta name="description" content="Descubre nuestros servicios de reparación de ordenadores, mantenimiento informático y asistencia técnica en Toledo.">

El contenido debe incluir:

  • Un h1 que resuma la página: Servicios de reparación informática en Toledo.
  • Tres apartados h2: reparación de ordenadores, mantenimiento preventivo y asistencia a empresas.
  • Un párrafo explicativo en cada apartado, con lenguaje natural.
  • Un enlace a contacto.html y otro de vuelta a index.html.
<main>
  <h1>Servicios de reparación informática en Toledo</h1>

  <section>
    <h2>Reparación de ordenadores y portátiles</h2>
    <p>
      Diagnosticamos y reparamos averías de hardware y software,
      sustituimos componentes y recuperamos equipos que han dejado de arrancar.
    </p>
  </section>

  <section>
    <h2>Mantenimiento preventivo</h2>
    <p>
      Limpieza interna, actualización de software y revisión de discos
      para alargar la vida útil de tus equipos.
    </p>
  </section>

  <section>
    <h2>Asistencia técnica para empresas</h2>
    <p>
      Soporte informático y mantenimiento de equipos para pequeños
      negocios y oficinas de Toledo.
    </p>
  </section>

  <p>
    <a href="contacto.html">Solicita información sobre nuestros servicios</a>
  </p>
</main>

Texto de enlace

Evita «Pincha aquí» o «Más información». El texto del enlace debe describir la página de destino: «Solicita información sobre nuestros servicios» aporta contexto al usuario y al buscador.

Comprueba

  • El title de servicios.html es distinto del de index.html.
  • La meta description también es distinta.
  • Hay un solo h1 y tres h2.
  • Los enlaces internos funcionan y usan rutas relativas.

04 Crear la página de contacto

La página de contacto también se posiciona: no la dejes sin metadatos.

Objetivo del paso

Crear contacto.html con información ficticia coherente, metadatos propios y navegación completa.

Incluye:

  • Un title como Contactar con TecnoSerprofes | Reparación informática en Toledo.
  • Una meta description que invite a contactar y mencione la ubicación.
  • Un h1 y, si añades horarios o dirección, un h2 para cada bloque.
  • Dirección, teléfono y correo ficticios pero verosímiles.

05 Incorporar imágenes optimizadas

El nombre del archivo y el atributo alt aportan contexto; el peso, velocidad.

Objetivo del paso

Añadir una imagen informativa a la portada con nombre descriptivo, formato moderno, dimensiones declaradas y un alt útil.

Prepara el archivo

  1. Descarga una imagen relacionada con la reparación de ordenadores.
  2. Redimensiónala al tamaño real de uso (por ejemplo, 1200 px de ancho).
  3. Conviértela a WebP si es posible.
  4. Guárdala en img/ con un nombre descriptivo: reparacion-ordenador.webp.

Evita nombres como IMG_20261113_001.jpg o foto final (1).JPG: no aportan información, usan mayúsculas y espacios, y algunos servidores los tratan de forma distinta. 

<img
  src="img/reparacion-ordenador.webp"
  alt="Técnico reparando la placa base de un ordenador de sobremesa"
  width="1200"
  height="800"
  loading="lazy"
>

El atributo alt describe la imagen a quien usa un lector de pantalla y aporta contexto a los buscadores. Debe ser específico y natural, no una lista de palabras clave. width y height reservan el espacio y evitan saltos de diseño (CLS).

Alt vacío, pero solo cuando toca

Si una imagen es puramente decorativa, usa alt="". Si es informativa, descríbela. Lo que no debe hacerse nunca es repetir la misma ristra de keywords en todas las imágenes.

Comprueba

  • La imagen se ve en la página y la ruta es relativa (img/...).
  • El nombre del archivo está en minúsculas y con guiones.
  • En DevTools, la imagen tiene alt, width y height.

Evidencia

Captura del código de la imagen y del archivo dentro de la carpeta img/.

07 URLs amigables y etiqueta canonical

Una misma página puede respondernos en varias direcciones. Hay que decir cuál es la buena.

Objetivo del paso

Entender qué hace amigable a una URL, comprobar las variantes que genera GitHub Pages y declarar la URL preferida con canonical.

Qué es una URL amigable

Una URL amigable es corta, descriptiva y legible: minúsculas, palabras separadas por guiones y sin parámetros innecesarios. Comunica el contenido antes de hacer clic y facilita el trabajo de los buscadores.

Comparación de URLs
URLValoración
/servicios/diseno-web/Amigable: descriptiva, en minúsculas y sin parámetros.
/pagina.php?id=27&cat=3Poco amigable: depende de identificadores.
/Servicios/Diseño Web.htmlProblemática: mayúsculas, espacio y tilde.
/p?=diseno_web_2026Confusa: parámetro sin estructura de carpetas.

El archivo que se sirve en un directorio

Los servidores web buscan un archivo de índice por defecto al acceder a una carpeta. Normalmente es index.html. Por eso una URL limpia como /servicios/ puede servir /servicios/index.html sin mostrar el nombre del archivo.

Ampliación: pasar de archivo a carpeta

En este proyecto hemos usado servicios.html por sencillez. En un sitio real conviene servicios/index.html para obtener /servicios/. Si lo haces, recuerda:

  • Cambiar los enlaces a servicios/ y contacto/.
  • Ajustar las rutas relativas dentro de la subcarpeta (../css/estilos.css, ../index.html).
  • Actualizar canonical y sitemap.xml con la URL final.
  • No mantener las dos versiones: generarías contenido duplicado.

Declarar la URL preferida

GitHub Pages responde tanto en https://usuario.github.io/ como en https://usuario.github.io/index.html. Son la misma página con dos direcciones. La etiqueta canonical indica cuál debe considerarse principal cuando hay contenido duplicado. 

<!-- En la portada -->
<link rel="canonical" href="https://usuario.github.io/">

<!-- En servicios.html -->
<link rel="canonical" href="https://usuario.github.io/servicios.html">

<!-- En contacto.html -->
<link rel="canonical" href="https://usuario.github.io/contacto.html">
  • Usa siempre URL absolutas, con https y el dominio completo.
  • Cada página apunta a sí misma, no a la portada.
  • No encadenes canonical: una canonical no debe apuntar a otra canonical.
  • La URL del canonical debe coincidir con la del sitemap.xml.

Canonical no es una redirección

canonical es una sugerencia de consolidación: Google puede ignorarla si detecta señales contradictorias. Para mover una URL de forma permanente se usa una redirección 301, que veremos en el paso 11.

Comprueba

  • Las tres páginas tienen un canonical distinto y absoluto.
  • Abre https://usuario.github.io/index.html: debe seguir funcionando, pero el canonical apunta a la raíz.
  • En DevTools → Elements, el canonical está dentro de <head>.

08 Crear robots.txt y entender noindex

Rastrear e indexar son cosas distintas. No las confundas.

Objetivo del paso

Crear un robots.txt válido, comprobar que se publica y diferenciar sus instrucciones de la directiva noindex.

En la raíz del proyecto crea robots.txt:

User-agent: *
Allow: /

Sitemap: https://usuario.github.io/sitemap.xml
Directivas básicas de robots.txt
DirectivaQué hace
User-agentIdentifica a los robots a los que se aplican las instrucciones. * significa todos.
AllowPermite el rastreo de una ruta.
DisallowPide a los rastreadores que no accedan a una ruta.
SitemapIndica la dirección del sitemap.

Qué pasa si bloqueas algo

User-agent: *
Disallow: /borradores/
Disallow: /admin/

Sitemap: https://usuario.github.io/sitemap.xml

robots.txt no borra del índice

robots.txt da instrucciones de rastreo. Si quieres que una página no aparezca en los resultados, usa noindex en su HTML. Y cuidado: si bloqueas la URL en robots.txt, el robot puede no llegar a leer el noindex.

La directiva noindex

<!-- Pide no incluir esta página en el índice -->
<meta name="robots" content="noindex, follow">
Diferencias entre noindex y robots.txt
Aspectonoindexrobots.txt
Dónde se declaraEn el <head> de la páginaEn un archivo de la raíz
Qué controlaLa indexaciónEl rastreo
Efecto sobre la URLPuede seguir apareciendo si está enlazada, pero sin contenido indexadoEl bot no visita la ruta
Uso típicoPáginas de agradecimiento, filtros, contenido duplicadoÁreas privadas, carpetas de desarrollo

Comprueba

  • https://usuario.github.io/robots.txt muestra el contenido en texto plano.
  • No hay líneas vacías entre directivas del mismo grupo.
  • La URL del Sitemap es absoluta y con https.

Evidencia

Captura del robots.txt abierto en el navegador desde la URL publicada.

09 Crear el sitemap.xml

Un mapa de las URLs importantes para facilitar su descubrimiento.

Objetivo del paso

Crear un sitemap.xml válido con las tres páginas publicadas y comprobar que Google puede leerlo.

<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://usuario.github.io/</loc>
    <lastmod>2026-11-13</lastmod>
  </url>
  <url>
    <loc>https://usuario.github.io/servicios.html</loc>
    <lastmod>2026-11-13</lastmod>
  </url>
  <url>
    <loc>https://usuario.github.io/contacto.html</loc>
    <lastmod>2026-11-13</lastmod>
  </url>
</urlset>
  • El sitemap enumera las URLs importantes y facilita su descubrimiento, sobre todo si hay muchas páginas o pocos enlaces internos.
  • Las direcciones deben coincidir exactamente con las URL publicadas y con el canonical.
  • No incluyas páginas que no existan, que devuelvan error o que tengan noindex.
  • Un sitemap no garantiza la indexación: es una ayuda, no una orden.

Errores que invalidan el XML

  • Olvidar el cierre </urlset>.
  • Usar rutas relativas en <loc>.
  • Dejar usuario sin sustituir por tu nombre de GitHub.
  • Guardar el archivo como sitemap.xml.txt.

Comprueba

  1. Abre https://usuario.github.io/sitemap.xml y revisa que el navegador no muestra errores de XML.
  2. Comprueba que cada <loc> responde con un 200.
  3. Valida el archivo con el validador de sitemaps o con Search Console.

Evidencia

Captura del sitemap.xml publicado y del resultado de la validación.

10 Crear una página 404 personalizada

Un error bien resuelto mantiene al usuario dentro del sitio.

Objetivo del paso

Crear 404.html, comprobar que devuelve el estado HTTP 404 y ofrecer rutas de salida al usuario.

En la raíz del proyecto crea 404.html:

<main>
  <h1>¡Vaya! No encontramos esta página</h1>
  <p>
    Puede que la dirección sea incorrecta o que la página ya no exista.
  </p>
  <p>
    <a href="/">Volver a TecnoSerprofes</a> ·
    <a href="/servicios.html">Ver nuestros servicios</a>
  </p>
</main>

GitHub Pages reconoce el archivo 404.html en la raíz y lo muestra cuando no encuentra una dirección. Debe conservar el mismo estilo visual que el resto de la web.

Soft 404: el error que engaña a Google

Una página 404 correcta devuelve el código de estado HTTP 404 y ofrece ayuda para seguir navegando. Si devuelve 200 se convierte en un soft 404: parece una página normal, Google la rastrea como válida y confunde a los usuarios. No redirijas siempre a la portada con JavaScript.

Comprueba

  1. Abre una URL inexistente, por ejemplo https://usuario.github.io/no-existe.
  2. En DevTools → Network, el documento debe mostrar 404.
  3. La página se ve con el diseño del sitio y tiene enlaces útiles.

Evidencia

Captura de la página 404 y del estado HTTP 404 en la pestaña Network.

11 HTTPS y redirecciones 301

La seguridad y los cambios de dirección también son SEO técnico.

Objetivo del paso

Activar HTTPS en GitHub Pages, entender qué es una redirección 301 y saber qué alternativas hay cuando el hosting no permite configurarlas.

HTTPS en GitHub Pages

  1. Entra en el repositorio → Settings → Pages.
  2. En Enforce HTTPS, activa la casilla.
  3. Espera a que GitHub emita el certificado y comprueba que http:// redirige a https://.

HTTPS cifra la conexión y es una señal de confianza para usuarios y buscadores. En GitHub Pages es gratuito y automático para dominios github.io.

Qué es una redirección 301

Una redirección 301 indica que una URL se ha movido de forma permanente a otra. Se usa al cambiar rutas o dominios, y ayuda a conservar las señales y la experiencia de los usuarios. Conviene apuntar directamente al destino final y evitar cadenas de redirecciones.

Códigos que debes reconocer
CódigoSignificadoUso típico
200OKPágina disponible
301Movido permanentementeCambio de URL o dominio
302Movido temporalmentePromociones o pruebas

Limitación de GitHub Pages

GitHub Pages no permite configurar redirecciones 301 del servidor ni cabeceras personalizadas. 12 Añadir Open Graph para redes sociales

Controla cómo se ve tu página cuando la comparten.

Objetivo del paso

Añadir etiquetas Open Graph a la portada y comprobar la vista previa en una red social o validador.

Cuando compartes una página en una red social o en una aplicación de mensajería, aparece una imagen, un título y una descripción. Open Graph permite controlar parte de esa información. 

<meta property="og:title" content="Reparación de ordenadores en Toledo | TecnoSerprofes">
<meta property="og:description" content="Servicio técnico y mantenimiento informático para particulares y empresas en Toledo.">
<meta property="og:type" content="website">
<meta property="og:url" content="https://usuario.github.io/">
<meta property="og:image" content="https://usuario.github.io/img/reparacion-ordenador.webp">
<meta property="og:locale" content="es_ES">
  • og:title, og:description y og:image son los tres campos imprescindibles.
  • La imagen debe ser absoluta, pública y de al menos 1200 × 630 px para verse bien en la mayoría de plataformas.
  • og:type suele ser website en portadas y article en entradas de blog.

Open Graph no es un factor de ranking

Mejora la presentación y el CTR social, pero no posiciona por sí mismo en Google. No lo confundas con los datos estructurados, que verás en la actividad 2.

Comprueba

  1. Pega la URL publicada en el validador de Open Graph o en el depurador de la red social.
  2. Deben aparecer el título, la descripción y la imagen correctos.
  3. Si la imagen no sale, revisa que la ruta sea absoluta y que el archivo exista.

Evidencia

Captura de la vista previa generada al compartir la URL.

13 Publicar la web con GitHub Pages

Del ordenador local a una URL pública y rastreable.

Objetivo del paso

Crear el repositorio, subir los archivos y activar GitHub Pages en la rama main.

  1. Entra en GitHub y pulsa New repository.
  2. Llama al repositorio usuario.github.io, sustituyendo usuario por tu nombre de GitHub.
  3. Marca el repositorio como Public y créalo.
  4. Sube index.html, servicios.html, contacto.html, 404.html, robots.txt, sitemap.xml y las carpetas css/ e img/.
  5. Ve a Settings → Pages.
  6. En Build and deployment, elige Deploy from a branch, rama main y carpeta /(root).
  7. Pulsa Save y espera a que termine la publicación.

Al llamar al repositorio usuario.github.io obtienes una User Site publicada directamente en https://usuario.github.io/, sin subcarpeta.

Rutas que se rompen al publicar

Si en local abres los archivos con file:///, algunas rutas parecen funcionar y en GitHub Pages fallan. Prueba siempre con Live Server y revisa que las rutas sean relativas y respeten mayúsculas y minúsculas.

Comprueba

  • https://usuario.github.io/ carga la portada.
  • Los enlaces a servicios y contacto funcionan.
  • La imagen y los estilos se cargan (mira la pestaña Network: no debe haber 404).
  • /robots.txt y /sitemap.xml se muestran.

Evidencia

URL pública y captura de Settings → Pages con el despliegue correcto.

14 Verificar el sitio en Google Search Console

Comunicar a Google que el sitio existe y comprobar cómo lo ve.

Objetivo del paso

Añadir la propiedad, verificarla con una etiqueta HTML, enviar el sitemap y solicitar la indexación de la portada.

Qué es Search Console

Es una herramienta gratuita de Google que permite comprobar si Google puede acceder a la web, consultar la indexación, enviar sitemaps, revisar problemas de rastreo y ver las búsquedas que generan impresiones y clics cuando hay datos suficientes.

Pasos

  1. Entra en https://search.google.com/search-console/ con tu cuenta de Google.
  2. Pulsa Añadir propiedad y elige Prefijo de URL.
  3. Introduce la dirección completa publicada, con https:// y barra final: https://usuario.github.io/.
  4. Elige el método de verificación Etiqueta HTML.
  5. Copia la etiqueta que te da Google y pégala dentro del <head> de index.html.
  6. Sube el cambio a GitHub, espera a que se publique y pulsa Verificar.
  7. Entra en Sitemaps, escribe sitemap.xml y pulsa Enviar.
  8. Usa Inspección de URLs con la portada y, si aún no está indexada, pulsa Solicitar indexación.
<meta name="google-site-verification" content="CODIGO_PROPORCIONADO_POR_GOOGLE">

No borres la etiqueta

Si eliminas la etiqueta de verificación, Google puede retirar la propiedad. Tampoco esperes indexación inmediata: puede tardar días o semanas y no está garantizada.

Comprueba

  • La propiedad aparece como verificada.
  • El sitemap figura como enviado y sin errores.
  • La inspección de la portada muestra que la URL está en Google o permite solicitar su indexación.

Evidencia

Captura de la propiedad verificada, del sitemap enviado y de la inspección de URL.

15 Medir con Lighthouse y PageSpeed Insights

Detectar problemas es más útil que perseguir una puntuación perfecta.

Objetivo del paso

Obtener un informe de rendimiento, accesibilidad, buenas prácticas y SEO, y proponer dos mejoras concretas.

  1. Abre la web publicada en Chrome.
  2. Pulsa F12 y entra en la pestaña Lighthouse.
  3. Selecciona Rendimiento, Accesibilidad, Buenas prácticas y SEO.
  4. Genera el informe en modo móvil.
  5. Repite la medición en https://pagespeed.web.dev/ para obtener datos de laboratorio y, si existen, de campo.

Si no hay datos de campo

PageSpeed Insights puede no tener datos reales de un sitio nuevo o con pocas visitas. En ese caso, trabaja con los datos de laboratorio de Lighthouse e indícalo en la entrega.

Comprueba

Evidencia

Informe en PDF o captura de las cuatro categorías y lista de dos mejoras propuestas.

Abrir el test de SEO básico

Autoevaluación

Responde antes de desplegar la respuesta. Si fallas, vuelve al paso indicado.

¿Por qué no conviene repetir el mismo title en todas las páginas?

Porque cada página compite por una intención distinta. Si comparten título y descripción, los buscadores no pueden distinguirlas y ambas pierden relevancia. Además, el usuario ve resultados duplicados y baja el CTR. Cada página debe tener un título único, descriptivo y con su keyword principal. Ver paso 2.

¿Un robots.txt con Disallow: / elimina la web de Google?

No. Solo impide el rastreo. La URL puede seguir apareciendo en el índice si tiene enlaces externos. Para excluirla del índice hay que usar noindex, y no conviene combinarlo con un bloqueo en robots.txt, porque el robot podría no llegar a leer la directiva. Ver paso 8.

¿Para qué sirve el canonical y en qué se diferencia de una 301?

El canonical indica cuál es la URL preferida cuando hay varias versiones del mismo contenido; es una sugerencia. Una 301 es una redirección permanente del servidor: lleva al usuario y al bot a la nueva URL y transmite la autoridad. Ver pasos 7 y 11.

¿Qué diferencia hay entre un 404 y un soft 404?

Un 404 devuelve el código HTTP 404 y avisa de que la página no existe. Un soft 404 devuelve 200 con un mensaje de error, así que el buscador lo trata como una página válida. Es un problema habitual en páginas que redirigen siempre a la portada con JavaScript. Ver paso 10.

¿Por qué el sitemap.xml debe coincidir con el canonical?

Porque ambos comunican a Google cuál es la URL preferida. Si el sitemap incluye una variante con parámetros o con index.html y el canonical apunta a otra, se envían señales contradictorias y se reparte la autoridad. Ver pasos 7 y 9.

¿Open Graph mejora el posicionamiento en Google?

No es un factor de ranking directo. Controla cómo se muestra la página al compartirla en redes sociales y mensajería, lo que puede mejorar el CTR social. Para datos estructurados y resultados enriquecidos se usa Schema.org. Ver paso 12.
